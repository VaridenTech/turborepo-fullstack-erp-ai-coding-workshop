Part of the Retail ERP first-release spec (#1).

## What to build

Stores master data and the cross-cutting list foundation every later screen reuses.

- `Store` model (unique code, name) with a contract, a NestJS module implementing the oRPC routes, and an Administrator UI to create, edit, and list stores.
- Establish the shared list conventions: newest-first ordering, pagination, and loading/success/error states.
- Establish the shared Thai error envelope: error code, Thai message, optional affected-field list; never expose stack traces or database details.
- Authentication and role enforcement at the API for every route (not just hidden buttons).

`Covers:` MD-03 (stores), Section 6.2 (pagination, list states, newest-first), NFR-04 (error envelope + dual-layer validation), NFR-01 (auth + role enforced at the API).
`Demo:` An Administrator creates B01 Central Store and B02 Riverside Store, sees them in a paginated, newest-first Thai list with loading/empty/error states; submitting an invalid store renders the Thai error envelope.
`Seams:` 1 (API controller spec), 2 (Zod schema test), 3 (web component test).

## Acceptance criteria

- Creating a store with a unique code and name persists it and returns it; the list route returns stores newest-first with pagination. (Fails today: no Store model or routes exist.)
- A duplicate store code is rejected with the Thai error envelope (code + Thai message), observable at seam 1 and surfaced at seam 3.
- A blank/invalid name is rejected by the Zod schema (seam 2) and by the API (seam 1).
- An unauthenticated request to any store route is rejected at the API; a non-Administrator is rejected by role enforcement, observable at seam 1.
- The store list screen renders loading, populated, and empty states and shows Thai copy, observable at seam 3.
